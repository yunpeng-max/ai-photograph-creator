## 6.1 前后端分离架构

```
┌─────────────┐     HTTP/JSON     ┌─────────────┐
│   前端        │ ◄──────────────► │   后端        │
│  (浏览器)     │    API 调用       │  (服务器)     │
└─────────────┘                   └──────┬──────┘
                                         │
                                         ▼
                                  ┌─────────────┐
                                  │   数据库      │
                                  └─────────────┘
```

**核心思想**：前端和后端是两个独立的项目，通过 HTTP API（通常是 JSON 格式）通信。

**好处**：
- 前端和后端可以独立开发、独立部署
- 同一个后端可以服务网页、手机 App、小程序等多种前端
- 各用各的技术栈（前端用 React，后端用 Python）

## 6.2 RESTful API 设计

这个项目的 API 遵循 REST 风格：

| 方法 | 路径 | 含义 |
|------|------|------|
| `POST` | `/auth/register` | 创建用户（注册） |
| `POST` | `/auth/login` | 登录（创建会话） |
| `GET` | `/auth/me` | 获取当前用户 |
| `POST` | `/generate` | 创建生成记录 |
| `GET` | `/generations` | 列表查询 |
| `GET` | `/generations/:id` | 查询单个 |
| `GET` | `/points` | 查询积分 |
| `GET` | `/options` | 查询选项 |

**设计原则**：
- 用 HTTP 方法表达操作意图（GET=读，POST=创建，PATCH=部分更新）
- URL 用名词（资源）而非动词
- 用 HTTP 状态码表达结果（200=成功，401=未认证，402=需要付费，409=冲突）

## 6.3 JWT 认证机制

JWT (JSON Web Token) 是现代 Web 应用最常用的认证方式：

```
┌──────────────┐                    ┌──────────────┐
│   客户端       │                    │   服务器       │
└──────┬───────┘                    └──────┬───────┘
       │  ① POST /login {email, pw}       │
       │ ─────────────────────────────────→│
       │                                   │ 验证密码
       │                                   │ 生成 JWT
       │  ② {token: "eyJ..."}             │
       │ ←─────────────────────────────────│
       │                                   │
       │  ③ GET /generations              │
       │  Header: Authorization: Bearer eyJ...│
       │ ─────────────────────────────────→│
       │                                   │ 验证 JWT
       │                                   │ 提取 user_id
       │  ④ {items: [...]}                │
       │ ←─────────────────────────────────│
```

**JWT 的结构**：`xxxxx.yyyyy.zzzzz`（三段，用点分隔）
- **Header**：令牌类型 + 签名算法
- **Payload**：实际数据（user_id, 过期时间等）
- **Signature**：对前两部分的签名，防止篡改

**关键特性**：
- **无状态**：服务器不需要存储会话，JWT 本身包含所有信息
- **防篡改**：修改任何内容都会导致签名不匹配
- **有过期时间**：过期后必须重新登录

## 6.4 ORM（对象关系映射）

ORM 让你用操作 Python 对象的方式操作数据库，不用写 SQL：

```python
# 不用 ORM（原始 SQL）
result = await db.execute("SELECT * FROM users WHERE email = :email", {"email": "user@example.com"})
user = result.fetchone()

# 用 ORM（SQLAlchemy）
result = await db.execute(select(User).where(User.email == "user@example.com"))
user = result.scalar_one_or_none()
```

**优势**：
- 防止 SQL 注入（参数自动转义）
- 类型安全（IDE 有代码提示）
- 数据库无关（换数据库不需改代码）
- 可读性好

**代价**：
- 性能略低于手写 SQL
- 复杂查询不如 SQL 灵活

## 6.5 异步编程 (async/await)

Python 的 `async/await` 和 JavaScript 的一样，用于处理 I/O 密集型操作：

```python
# 同步方式（会阻塞，一次只能处理一个请求）
def generate():
    user = db.query(User).where(...)       # 等数据库返回（阻塞）
    image = dashscope.call(...)            # 等 API 返回（阻塞）
    save(image)                            # 等磁盘写入（阻塞）
    return result

# 异步方式（不阻塞，并发处理多个请求）
async def generate():
    user = await db.execute(...)           # 数据库查询时，去处理其他请求
    image = await generate_image(...)      # API 调用时，去处理其他请求
    url = await save_image(image)          # 文件写入时，去处理其他请求
    return result
```

**核心思想**：等待 I/O 时不占着 CPU，让出执行权给其他任务。

## 6.6 依赖注入 (Dependency Injection)

FastAPI 的 `Depends()` 系统是本项目的关键设计模式：

```python
@router.get("/me")
async def me(current_user: User = Depends(get_current_user)):
    # current_user 由 FastAPI 自动注入，不需要手动获取
    return current_user
```

**好处**：
- 关注点分离：认证逻辑集中在 `get_current_user()`，接口只写业务代码
- 可测试：测试时可以替换依赖
- 可复用：多个接口共享同一个依赖

## 6.7 密码安全

```
用户输入密码 "mypassword123"
    ↓
bcrypt.hashpw() → "$2b$12$LJ3m4ys3GZfnYMz8kVsKaOGzGvF7XxLB..."
    ↓
存入数据库（只存哈希值）
    ↓
下次登录时：
用户输入 "mypassword123"
    ↓
bcrypt.checkpw("mypassword123", "$2b$12$LJ3m4...") → True ✓
用户输入 "wrongpassword"
    ↓
bcrypt.checkpw("wrongpassword", "$2b$12$LJ3m4...") → False ✗
```

**bcrypt 的特点**：
- **单向**：哈希值无法反推出原始密码
- **加盐**：同样的密码两次加密结果不同（防止彩虹表攻击）
- **慢**：故意设计成计算量大，增加暴力破解成本
- `$2b$12$`：2b=算法版本，12=计算强度（2¹²=4096 轮）

## 6.8 React 核心概念

### 组件化

```
<App>
  <AuthProvider>
    <LocaleProvider>
      <BrowserRouter>
        <Layout>                   ← 布局组件（侧边栏+顶栏）
          <HomePage>               ← 页面组件
            <Card>                 ← UI 组件
              <ChipSelector />     ← UI 组件
              <Input />            ← UI 组件
              <Button />           ← UI 组件
            </Card>
          </HomePage>
        </Layout>
      </BrowserRouter>
    </LocaleProvider>
  </AuthProvider>
</App>
```

每个组件只负责一件事，组合起来构建复杂界面。

### 状态 (State) 和属性 (Props)

```tsx
// State：组件内部的、可变的数据
const [form, setForm] = useState<FormData>(defaultForm);
// form 改变 → 组件重新渲染

// Props：父组件传给子组件的数据（只读）
<Button variant="primary" size="lg" loading={true}>
  生成图片
</Button>
// variant, size, loading 都是 props
```

> **核心原则**：数据向下流动（父→子通过 props），事件向上冒泡（子→父通过回调函数）。

### 副作用 (useEffect)

```tsx
useEffect(() => {
    // 组件挂载后执行（如加载数据）
    api.getOptions().then(setOptions);

    return () => {
        // 组件卸载前执行（如清理定时器）
    };
}, []);  // 空数组 = 只在挂载时执行一次
```

### Context（全局状态）

当很多组件都需要同一份数据时（如用户信息），用 Context 比一层层传 props 更优雅：

```tsx
const AuthContext = createContext(...);

// Provider：提供数据
<AuthContext.Provider value={{ user, login, logout }}>
  {children}
</AuthContext.Provider>

// Consumer：消费数据（任何后代组件都可以）
const { user } = useAuth();
```

## 6.9 环境配置管理

**为什么需要环境变量？**

```bash
# .env 文件（不提交到 Git）
OPENAI_API_KEY=sk-xxxxxx
SECRET_KEY=my-random-secret
DATABASE_URL=postgresql://...

# .env.example 文件（提交到 Git，作为模板）
OPENAI_API_KEY=your-api-key-here
SECRET_KEY=change-me
DATABASE_URL=postgresql://...
```

**核心原则**：密钥和密码永远不提交到代码仓库。`.env` 在 `.gitignore` 中，`.env.example` 作为模板提供。

## 6.10 Docker 容器化部署

```yaml
services:
  db:       # 数据库容器
    image: postgres:16-alpine
  backend:  # 后端容器
    build: ./backend
  frontend: # 前端容器
    build: ./frontend
```

**Docker 的好处**：
- 环境一致："在我电脑上能跑"的问题不再存在
- 一键启动：`docker-compose up -d`
- 隔离：每个服务在独立的容器中，互不影响
- 可扩展：加机器时直接启动新容器

## 学习建议

作为计算机专业学生，建议按以下顺序深入学习这个项目：

1. **先跑起来**：按照 README 的步骤启动项目，实际体验一下
2. **跟踪一个请求**：从点击"生成"按钮开始，在前端代码打断点，在后端代码打断点，看数据怎么流转
3. **改一个小功能**：比如给表单增加一个新的风格选项
4. **看数据库**：连上 PostgreSQL，看看三张表里实际存储了什么数据
5. **读 API 文档**：启动后端后访问 `http://localhost:8000/docs`，FastAPI 自动生成的 Swagger 文档
6. **理解架构决策**：为什么选 UUID 而不是自增 ID？为什么积分用流水模式？为什么提示词要组装？

## 三张表详解

### 1. users（用户表）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID | 主键，自动生成 |
| `email` | VARCHAR(255) | 唯一，建了索引（登录时快速查找） |
| `password_hash` | VARCHAR(255) | bcrypt 加密后的密码，**绝不存明文** |
| `nickname` | VARCHAR(100) | 显示名称 |
| `points_balance` | INTEGER | 积分余额，默认 5 |
| `locale` | VARCHAR(5) | 语言偏好，"zh" 或 "en" |
| `created_at` | TIMESTAMP | 注册时间 |
| `updated_at` | TIMESTAMP | 最后更新时间（自动更新） |

> **为什么密码字段叫 `password_hash` 而不是 `password`？** 提醒自己和他人：这里存的是哈希值，不是原始密码。

### 2. generations（生成记录表）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID | 主键 |
| `user_id` | UUID FK | 外键 → users.id |
| `image_type` | VARCHAR(50) | 如 "portrait", "product_photo" |
| `aspect_ratio` | VARCHAR(20) | 如 "16:9", "1:1" |
| `style` | VARCHAR(50) | 如 "cyberpunk", "realistic" |
| `scene` | VARCHAR(50) | 如 "night_city", "studio" |
| `whitespace` | VARCHAR(20) | 如 "some", "generous" |
| `subject` | TEXT | 用户输入的主体描述（可能很长） |
| `additional_requirements` | TEXT, NULLABLE | 额外要求，可选 |
| `assembled_prompt` | TEXT | 组装后的完整英文提示词 |
| `image_url` | VARCHAR(500), NULLABLE | 生成图片的本地 URL |
| `status` | VARCHAR(20) | "pending" / "completed" / "failed" |
| `cost_points` | INTEGER | 本次消耗积分，默认 1 |
| `created_at` | TIMESTAMP | 创建时间，建有索引 |

### 3. point_transactions（积分流水表）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID | 主键 |
| `user_id` | UUID FK | 外键 → users.id，建有索引 |
| `change_amount` | INTEGER | 变动金额：正数=增加，负数=扣减 |
| `balance_after` | INTEGER | 这笔交易后的余额 |
| `reason` | VARCHAR(50) | 原因标识（见下表） |
| `related_generation_id` | UUID FK?, NULLABLE | 关联的生成记录 |
| `created_at` | TIMESTAMP | 交易时间，建有索引 |

**积分原因 (reason) 枚举**：

| reason | 说明 |
|--------|------|
| `registration_bonus` | 注册奖励（+5） |
| `generation_cost` | 生成消耗（-1） |
| `generation_refund` | 生成失败退回（+1） |

## 数据库设计原则

### 1. 范式化设计

数据没有冗余。比如 `user.email` 只在 users 表存一份，generations 表通过 `user_id` 外键引用。

> **好处**：修改邮箱只需改 users 表一处，不会出现数据不一致。

### 2. 索引策略

| 索引 | 用途 |
|------|------|
| `users.email` UNIQUE | 登录时快速查用户，同时保证邮箱唯一 |
| `generations.user_id` | 快速查某个用户的所有生成记录 |
| `generations.status` | 按状态筛选（如找所有失败的生成） |
| `generations.created_at` | 按时间排序（历史记录按最新排列） |
| `point_transactions.user_id` | 快速查某个用户的积分流水 |
| `point_transactions.created_at` | 按时间排序流水 |

> **索引是什么？** 就像书的目录。没有索引，数据库要逐行扫描；有了索引，直接跳转到目标位置。但索引有代价——每次写入数据都要更新索引。

### 3. 流水记录（审计日志）

积分系统采用**流水记录模式**而非简单的字段更新。每次积分变动都留下一条 `point_transactions` 记录，包括：
- 变了多少（change_amount）
- 变动后余额（balance_after）
- 为什么变（reason）
- 关联的业务记录（related_generation_id）

> **好处**：
> 1. 可以追溯任意时刻的积分余额
> 2. 用户有争议时可以查流水对账
> 3. 便于数据分析（如统计积分消耗趋势）

### 4. 外键约束

所有 `user_id` 和 `related_generation_id` 都有外键约束，保证数据完整性：
- 不能插入一个不存在的 user_id
- 删除用户时会失败（因为有子记录），防止误删

## 一些 SQL 示例

虽然项目用了 ORM，但理解背后的 SQL 有助于深入理解：

```sql
-- 注册用户
INSERT INTO users (id, email, password_hash, nickname, points_balance, locale)
VALUES ('abc-123', 'user@example.com', '$2b$12$...', '张三', 5, 'zh');

-- 记录积分流水
INSERT INTO point_transactions (user_id, change_amount, balance_after, reason)
VALUES ('abc-123', 5, 5, 'registration_bonus');

-- 查看某用户的所有生成记录（按时间倒序）
SELECT * FROM generations
WHERE user_id = 'abc-123'
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;

-- 扣积分（原子更新）
UPDATE users
SET points_balance = points_balance - 1
WHERE id = 'abc-123' AND points_balance >= 1;  -- 防止减成负数

-- 查积分流水
SELECT * FROM point_transactions
WHERE user_id = 'abc-123'
ORDER BY created_at DESC
LIMIT 50;
```
